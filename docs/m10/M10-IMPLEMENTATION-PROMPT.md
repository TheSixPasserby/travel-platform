## 2. 顶栏和导航（第一优先级）

### 2.1 桌面单行布局

**以 `references/01-desktop-single-row-header.png` 的水平结构为主要参考。** 本次设计图是静态概念稿，不是现有站点截图；实际使用既有品牌 Token、可访问性规则及路由。

**严格按如下信息结构：**

```text
┌──────────────────────────────────────────────────────────────────────┐
│ ☰  [山水间 Logo]   [探索] [攻略] [目的地] [AI 行程]      [⚙] [头像] │
└──────────────────────────────────────────────────────────────────────┘
```

- 顶栏容器任何登录状态下均只有**一行**；不得因菜单项、头像、登录按钮或窗口缩窄换成两排。
- Logo 位置与品牌识别保持统一；桌面常用快捷入口最多 3–4 个，根据实际路由使用“探索/攻略/目的地/AI 行程”等合适名称；当前所在路由有明显选中态。
- 右侧设置和账号区域位置固定，登录状态变化不引起大幅跳动。
- 响应式：桌面完整快捷入口；中等宽度优先减少快捷项或文字；窄屏只保留左侧菜单与 Logo、右侧设置与头像/登录。避免横向溢出。
- 顶栏在深浅色主题下视觉一致，保留现有“山水间”配色与字体，不直接照搬 Google 品牌。
- 顶栏可以适度 sticky，但若影响现有布局和移动键盘则不强制。

### 2.2 抽屉菜单

以 `references/02-mobile-navigation-drawer.png` 为参考，桌面点击汉堡按钮也使用同类型抽屉。

- 所有尺寸左上角都有菜单按钮 `☰`。
- 点击后从左侧滑入抽屉，页面背景有遮罩，内容不被强行挤压。
- 分组建议：**发现**（首页、攻略、目的地、AI 行程）、**我的**（我的攻略、收藏、行程、写攻略；未登录时给登录引导）、**管理**（仅 ADMIN 可见）。
- 当前路由高亮；关闭后焦点回到触发按钮。
- 点击遮罩、按 Escape、选择菜单项后自动关闭；抽屉打开时背景滚动锁定，关闭后恢复。
- 抽屉内容可单独滚动；高度适配手机安全区域、浏览器地址栏变化与软键盘。
- 不因为只是前端隐藏管理员入口就放弃后端权限校验。

### 2.3 设置浮层

以 `references/03-mobile-settings-popover.png` 为参考：三态切换是 P0，预览块是说明性装饰而非必须功能。

- 右侧头像左边放设置齿轮按钮。
- 点击弹出锚定浮层/小面板，桌面右上角定位，手机保持视口内可操作。不要跳转整页。
- **本次至少提供“浅色 / 深色 / 跟随系统”**，复用现有 theme store，实时生效，刷新持久，支持系统主题变化。
- 其余设置（例如动效偏好）可以预留，不放置无效或无法保存的假开关。
- 抽屉、设置和账号面板互斥；遮罩、键盘与焦点管理符合可访问性要求。

### 2.4 账号浮层与未登录状态

以 `references/04-mobile-account-popover.png`、`references/06-mobile-signed-out-light.png` 对照已登录/未登录状态。

- 已登录：右上角显示本人头像，点击弹出账号卡片：头像、**昵称**、灰色 `@username`，以及个人中心、我的攻略、收藏、行程、退出登录。

## 3. 用户身份：昵称与用户名

### 3.1 数据与账号约定

- 现有 `username` 已唯一、可登录；`nickname` 已独立。**不要修改密码登录策略、不增加重复字段、不让昵称承担唯一性。**
- `username` 保持稳定唯一标识；昵称允许用户在现有个人资料页面修改，昵称重复应允许。
- 昵称为空的历史异常记录可展示回退用户名，但不要无依据批量更新用户资料。
- Web 用户显示统一使用 `昵称` + 下方灰色小字 `@username`；避免串成一行很长的文本造成溢出。

### 3.2 API 最小兼容扩展

- 在**公开**用户信息 `PublicProfileVO` 中安全地新增 `username`，更新攻略作者、评论作者及必要的公开用户资料返回值；当前用户资料原本已包含 username 的地方不要重复处理。
- 同步 TS 类型与 Vue 展示组件。可新建 `UserIdentity.vue` 复用头像、昵称、账号展示；不允许引入重量级 UI 依赖。
- 不输出密码哈希、token、邮箱、电话号码或内部安全字段。
- **兼容移动端**：新增字段应为向后兼容扩展；移动端旧页面仍可正常展示。若共享 TS 类型修改导致移动端类型检查报错，应同步最小必要改动，但暂不重做 uni-app 视觉布局。
- 公开 `@username` 可能提高账号可枚举性，不能因此放宽认证错误响应、登录频率限制或用户隐私边界。

### 3.3 覆盖位置

- 顶栏用户卡片；
- 个人中心；
- 攻略作者区（详情页、适合的卡片列表）；

## 4. 评论区优化 + 攻略/评论 IP 归属地

### 4.1 评论 UI

以 `references/05-guide-comments-ip-region.png` 作为视觉层级参考；图中的评论文案、用户名及属地为占位示例，不得写进业务数据库或当成真实 IP 来源。

继续使用现有 `GuideComments.vue` 及 API。保留分页、评论计数、创建、删除、403/404、审核隐藏、账号切换防竞态。调整每条评论的信息层级：

```text
[头像] 昵称                 [作者]（按实际用户ID判断）
       @username · 2026-11-07 · IP 属地：四川
       评论正文，可换行，长文本安全展示
       [删除]（仅本人可见且后端仍校验）
```

- 灰色次级信息适当换行、手机宽度不溢出。
- 昵称可与攻略作者本人比较 `author.id` 展示“作者”标记；不要把任何人都标为作者。
- 未登录允许阅读公开正常评论，登录后才能发言。
- 评论输入、长度、分页、发送状态、重试、失败保留文本等原逻辑不退化。
- 不要求本轮实现二级回复、点赞评论或评论树；避免冲刺延期。

### 4.2 IP 归属地边界（重要）

**需求是 IP 属地，而不是 GPS / 精确位置。**

- 攻略：记录**首次公开发布时**服务端可信请求 IP 对应的粗粒度地域文本；之后编辑、撤回再发布不随意改写历史首次发布时间对应的属地（特殊情况以真实状态机为准，须记录决策）。
- 评论：记录**发表时**的粗粒度地域文本。
- 旧攻略与旧评论由于没有可靠的历史 IP，不可根据作者当前 IP、登录记录或服务器所在城市补填；保留 NULL，显示 `IP 属地：未知` 或不展示。
- 前端**只展示省/直辖市/特别行政区/国家等粗粒度文本**，不暴露真实 IP、精确经纬度、详细地址或精细设备信息。可优先按国内省级、境外国家级；不要展示“IP=xxx.xxx.xxx.xxx”。
- 只在真实写操作时由**后端**计算，不接受客户端随请求提交的 `ipRegion`/原始 IP。浏览器定位权限与此无关，不应请求 GPS。
- 不得根据随意的 `X-Forwarded-For` 或 `X-Real-IP` 头直接信任客户端。仅当**请求来自已明确配置的可信反向代理**时，才按受控规则解析转发链；否则使用实际远端地址。应覆盖 IPv4/IPv6、IPv4-mapped IPv6、回环、RFC1918 私网、非法/伪造转发头。
- 建议封装 `ClientIpResolver` + `IpRegionResolver`，使用**可审计的 GeoIP 数据来源**（自带合法许可证的本地库或可明确配置的可靠服务）并记录版本/来源与缓存策略。不要硬编码“所有国内 IP 都是四川”，不要基于字符串前缀猜省份。
- 如果当前没有合法可用的地域库/服务或 API Key，**不要为赶工伪造 IP 属地**：采用 `未知` 降级，保证正常发布与评论。不要为此让关键写业务依赖外部网络同步成功。
- 不引入未经授权的 GeoIP 下载站点或不透明第三方上报；如采用外部服务，先明确用户隐私/费用/可用性边界，避免未经批准向第三方发送访问者 IP。
- 数据库优先只保存粗粒度 `ip_region`（可空），**不新增永久存储原始 IP 的公开业务字段**。日志依现有项目政策脱敏/控制保留；不要将全量请求 IP 暴露在诊断日志或响应里。
- 地域信息应在 UI 明确标为 `IP 属地`，不冒充常住地、旅行目的地、户籍或实时物理位置；遵守适用隐私告知与保留约定。

### 4.3 数据库与 API

- 先检查后端实体、Mapper、DTO、VO 和现有迁移工具。若不存在字段，设计新的**增量、可验证、可恢复**的迁移，建议 `guides.ip_region` 与 `guide_comments.ip_region` 可空，避免强制给历史数据填值。
- 绝不重跑 `database/schema.sql` 去升级现有库，更不能删表重建。
- 先独立测试库验证，再经过备份和目标确认执行开发库迁移；不自动操作生产库。
- 服务端发布/写评论流程只写自己计算的属地，API 返回 `ipRegion` 或项目现有风格的字段，公开攻略详情/评论列表适用，私有资源规则保持不变。
- 攻略编辑不允许篡改属地；管理后台治理不应修改历史属地。
- 旧接口字段保留，新增字段尽量向后兼容；旧移动端无需在本轮新增属地 UI，但构建必须仍通过。
- 对数据迁移、读写、并发和失败降级增加实际测试。
