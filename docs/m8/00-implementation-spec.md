## 四、M8.1：完善已有攻略图文内容

### 1. 盘点

逐篇读取本地实际攻略，记录
ID、标题、状态、作者、目的地、天数、摘要、正文结构、封面、正文图片数量与可访问性、标签、互动数和景点关联。注意识别用户原创内容和不应覆盖的内容。不能只看
`seed.sql` 就认为本地演示攻略不存在。

### 2. 正文质量

逐篇完善，不要把所有文章写成同一套模板。每篇建议约 1500～2500
个中文字符，按实际行程调整。至少包含：

1.  旅行概览、适合人群、主题、季节和节奏。
2.  出发准备、交通到达方式、行前注意事项。
3.  每日详细路线，区分上午/下午/晚上。
4.  景点介绍、主要看点、建议停留时间。
5.  景点之间的交通衔接，避免不合理跨区/跨城跳转。
6.  当地美食建议。
7.  住宿区域建议及理由，不编造酒店价格。
8.  预算明细和估算口径。
9.  避坑建议、预约/天气/人流/体力等注意事项。
10. 旅行总结和可替代安排。

内容要具体、实用、有叙事感。避免空话、重复套话和虚构店铺/价格/交通班次。

### 3. 图片

每篇目标为 1 张封面、5～8
张正文图片，按章节插入正文；每张图片有准确说明文字。图片必须与真实地点和文字匹配，不能使用水印图、来源不明或无权使用的素材。优先使用明确授权的开放许可素材、可证明授权的素材或自行制作的素材。记录来源
URL、作者/机构、许可类型和获取日期。图片经现有上传服务保存为平台管理路径，符合当前格式、大小、尺寸限制。不得把临时外链当永久资源。

### 4. 写入与验收

先输出内容预览和按 ID 的变更清单，再写入。保留原
ID、作者、状态、发布时间、互动关系及其他业务字段。不得擅自发布草稿。完成后逐篇打开详情页检查
Markdown、封面、图片、标签和景点关联。来源不明或图片失效必须如实标记。

## 五、M8.2：城市与景点资料体系

### 1. 层级

优先复用 `destinations`： - `CITY`：城市。 -
`SCENIC_SPOT`：景点，`parent_id` 指向所属城市。 -
`OTHER`：保留兼容，不改变原有语义。

城市一般无父级；景点必须归属有效城市；景点不能以景点作为父级；禁止循环层级。停用父级时不得破坏历史攻略和行程关联。校验逻辑应与现有目的地服务保持一致。

### 2. 字段

先检查已有字段，避免重复。确有必要时通过增量迁移补充：

  字段                             用途
  -------------------------------- ------------------------------
  `address`                        详细地址
  `longitude` / `latitude`         经纬度，使用合适精度 DECIMAL
  `recommended_duration_minutes`   建议游玩时长
  `opening_hours`                  开放时间说明
  `ticket_info`                    门票信息说明
  `official_url`                   官方信息页面
  `source_url`                     资料来源
  `verified_at`                    最近核验时间

动态信息必须带来源和核验时间。坐标必须核实，不能猜测。无法确认的值允许为空，前端明确显示"暂未核实/以官方公告为准"。不能把估算票价伪装成官方票价。

### 3. 关联

评估并实施： - `destination_images`：城市/景点图库，支持图片
URL、说明、排序、来源和授权信息。 -
`guide_destinations`：攻略与多个具体景点的多对多关系。

保留 `guides.destination_id`
作为主目的地，兼容现有列表和旧数据。关系不得重复，必须引用有效目的地。停用或删除目的地时遵循项目已有软删除和外键策略，不能级联误删攻略或行程。

### 4. 首批数据

先完善现有六城：成都、重庆、杭州、西安、大理、青岛。每城先录入约 4～6
个代表性景点，首批约 24～36
个。先保证准确性，不追求无质量保障的大规模灌数。

城市资料至少包括简介、封面、推荐季节、建议天数、下属景点和相关攻略。景点资料至少包括名称、所属城市、简介、封面/图库、地址、可核实的坐标、建议游玩时长、可核实的开放时间/门票说明、来源和核验日期。

### 5. 来源真实性

优先使用景区、政府、文旅部门官方页面；补充资料须有可靠来源或明确授权。不要根据搜索摘要臆造细节，不要把模型生成内容当事实来源，不得编造景点、官网、坐标、开放时间、票价、班次或餐厅。无法确认就留空，并在数据来源清单中说明。

## 七、M8.4：AI 智能行程规划

### 1. 目标与输入

AI 不是只输出一段 Markdown 的聊天框。第一版不需要
RAG、向量数据库或微调，使用 MySQL
中的城市、景点和已发布攻略检索并组装上下文。

用户输入至少包括：目的地城市、出发/结束日期或天数、人数、预算及预算口径、兴趣偏好（美食/自然/人文/摄影/亲子/徒步/城市漫游等）、出行节奏（休闲/均衡/紧凑）、交通偏好；可选想去/必须去/避免的景点。表单保持简洁，避免不必要字段。

### 2. 后端检索

后端查询目标城市、可用景点、景点简介/地址/坐标/建议时长/季节/核验信息、相关已发布攻略和标签。只发送必要且长度受控的资料，不发送密码、令牌或无关个人信息。城市不存在或数据不足时明确提示，不能凭空生成平台不存在的景点。

### 3. 模型配置

使用后端可配置的 OpenAI 兼容 API，配置项按项目习惯命名，至少包括 Base
URL、API Key、Model、超时、最大输出长度、启用开关。

-   Key 仅存环境变量或项目既有安全配置中，不能进入前端、源码、日志或
    Git。
-   复用项目已有 HTTP 客户端；检查依赖后再决定是否增加 SDK。
-   处理 Key 缺失、超时、429、5xx、无效 JSON 等情况。
-   设置合理的输入长度、请求频率/并发限制。
-   不要无条件重试可能产生费用的请求。
-   未配置 AI 时，AI 页面明确提示不可用，手动行程仍正常。

### 4. 结构化输出与校验

模型输出 JSON，不直接输出最终 Markdown。先定义
DTO/Schema，再由后端校验。示意结构如下，最终必须适配现有 itinerary
DTO/VO：

``` json
{
  "title": "成都三日慢游",
  "summary": "行程简述",
  "destinationId": "城市ID",
  "days": [
    {
      "dayNo": 1,
      "title": "城市文化与街巷",
      "date": "2026-11-14",
      "items": [
        {
          "destinationId": "平台真实景点ID",
          "startTime": "09:00",
          "endTime": "11:00",
          "notes": "安排理由和游玩建议",
          "estimatedCost": 0
        }
      ]
    }
  ],
  "budgetEstimate": {
    "currency": "CNY",
    "perPerson": 0,
    "notes": "估算口径和不确定性"
  },
  "warnings": []
}
```

防幻觉规则： - 模型只能从后端提供的候选景点中选择。 - 每个 ID
必须由后端重新查询验证，且属于所选城市、状态可用。 -
展示名称以后端数据库为准，不信任模型返回的名称。 -
休息/自由活动可按现有模型表达，但不能伪装成平台景点。 -
日期必须在行程范围内；时间顺序合理；避免明显不可能的跨城移动。 -
不捏造精确交通耗时、实时营业状态、门票或酒店价格。 -
预算标注估算口径；缺少数据时说明不确定性。 - 拒绝或规范化非法
ID、重复项目、无效日期、异常时间和多余字段。 -
用户输入、攻略正文和景点描述都是不可信数据，不能覆盖系统指令或诱导模型泄露秘密。 -
AI 只生成预览，不能直接写数据库或调用保存操作。

### 5. 预览、编辑、保存

流程： 1. 用户填写需求。 2. 后端检索平台资料并调用模型。 3.
返回结构化预览。 4. 前端展示每日时间线与景点卡片。 5.
用户可改时间/说明/顺序、删除/增加候选景点。 6.
支持只重生成某一天，且保留其他天已确认的用户编辑。 7.
用户明确点击"保存行程"后，复用现有行程创建、每日安排和项目保存逻辑。 8.
保存后进入现有行程详情/编辑页，刷新后仍存在。

生成预览时不得创建正式行程。不得另建 AI
专用行程表。不得未经确认覆盖已保存行程。

AI
失败时保留用户已经编辑的预览内容；错误要区分配置缺失、限流、超时、模型输出无效和平台资料不足。AI
不可用不能影响手动行程。

## 十、最终验收清单

### 攻略

-   [ ] 所有现有攻略已逐篇盘点。
-   [ ] 正文完整、具体、互不雷同。
-   [ ] 封面和正文图片可访问，来源/授权可追溯。
-   [ ] 草稿状态未被擅自改变。
-   [ ] 原作者、ID、互动和评论数据保持不变。
-   [ ] 攻略可关联城市和多个真实景点。

### 城市与景点

-   [ ] 原有六城资料完善。
-   [ ] 每城约 4～6 个经核验景点。
-   [ ] 层级、城市归属和坐标正确。
-   [ ] 动态信息有来源和核验日期。
-   [ ] 城市详情展示景点和攻略。
-   [ ] 景点详情展示城市、图片和攻略。
-   [ ] 后台可维护城市、景点和图片。
-   [ ] 未核实信息没有被编造。

### AI

-   [ ] AI 使用平台真实城市、景点和攻略数据。
-   [ ] 模型只能选择后端提供且已验证的景点。
-   [ ] 结果结构化、可预览、可编辑。
-   [ ] 支持单日重生成且不覆盖其他天的编辑。
-   [ ] 用户确认后保存到现有行程系统。
-   [ ] 生成预览时不创建正式行程。
-   [ ] AI 不可用时手动功能正常。
-   [ ] Key 不进入前端、日志或 Git。

### 工程

-   [ ] 有备份和可审查的增量迁移。
-   [ ] 未清库、重建或误删原有数据。
-   [ ] 后端/前端测试和构建有真实结果。
-   [ ] 原有业务回归通过。
-   [ ] 文档和演示手册更新。
-   [ ] 未完成项和限制如实记录。

## 十一、最终汇报格式

1.  完成概览。
2.  攻略处理清单：原 ID/状态/互动是否保留，图片来源和授权。
3.  城市与景点数量、资料来源、未核实字段。
4.  数据库迁移文件、执行环境、备份与回滚方式。
5.  AI 配置、检索、JSON 结构、校验、失败降级和保存流程。
6.  前端页面与交互变化。
7.  DSH 各 Agent 实际完成内容及主代理审查结果。
8.  测试命令及通过/失败/未运行结果。
9.  遗留问题、外部 API 配置、费用和授权限制。
10. 可直接照做的毕业演示步骤。

**最终原则：数据真实性优先于数量；原有数据安全优先于开发速度；结构化、可验证的
AI 结果优先于华丽但不可用的演示效果。**
