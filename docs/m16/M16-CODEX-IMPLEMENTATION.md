## 1. P0：全站统一搜索（建议 M16.1）

**现状**：`frontend/src/api/guides.ts` 有指南查询和游标信息流；目的地/公开作者/标签 API 已存在，但**没有已核实的统一跨类型搜索 API**。先读现有 API/Mapper，然后选择最少新增的接口：优先复用各类型业务查询；若需要一体化接口，新增只读 `/api/v1/search` 和有类型的 DTO/VO（参见契约文件），不要引入 Elasticsearch、Redis、向量搜索。

**体验**：统一搜索入口；关键字、搜索建议、历史（仅当前浏览器，可清空）、标签和类型 Tabs；结果独立显示“攻略/目的地/景点/作者/话题”。空态/加载/错误/重试/退格/URL 恢复；鼠标与键盘导航。搜索提示防抖、最新请求获胜、移动端输入法拼写未完成时不提前搜索。结果点击必须去真实 `/guides/:id`、`/destinations/:id`、`/users/:username` 等路由；不得暴露草稿、被隐藏/删除内容或私人行程。搜索建议来自真实公开内容或明确标记的本地历史，不能伪造。

**排序**：默认相关性（字段匹配与基础新鲜度）；“最新”保持服务器稳定排序；不得把热门排序冒充个性化。查询绑定、排序游标/分页及 URL 前后退应兼容 M13 信息流；不能因搜索新功能退回笨重数字分页。

**DSH 前端文件候选**：`frontend/src/components/SiteHeader.vue`、新的 `SearchView.vue` / `SearchSuggestions.vue` / `SearchResultCard.vue`、`frontend/src/router/index.ts`（路由主代理统筹）、`frontend/src/styles`、组件测试。Codex 负责后端契约、搜索端点、数据权限/性能测试。

**完成判定**：用户搜索“成都”能从一页找到公开攻略、城市/景点、作者/话题；不存在的关键词出现有意义空态；全部实体链接真实可用；匿名用户可搜公开内容但写操作必须登录；不同屏幕与主题下无溢出。

## 2. P0：攻略 / 收藏 → 加入行程（建议 M16.2，最高价值）

**现状关键**：攻略详情已有 `destination`、`scenicSpots` 等受管关联；`frontend/src/api/itineraries.ts` 有创建行程、天、项目、排序与完整 AI 行程导入；`frontend/src/types/ai.ts` 的 `AiRequirements` 已含 `cityId`、`preferredIds`、`mustVisitIds`、`avoidIds`、日期、预算、步调和交通。优先复用 **真实关联景点 ID**，不要仅从 Markdown 正文中猜测新景点，更不能把所有文本中的地名当已核实景点。

**用户流程**：在攻略详情右侧操作栏新增“加入行程”；收藏页的攻略卡也可进入该流程；弹出统一的 `AddToTripDrawer`，展示真实、允许访问的关联目的地和景点；用户逐一勾选→选已有私人行程/指定日期或新建→预览冲突与重复→明确确认→服务端创建→成功后给出“查看我的行程”入口。无已关联景点时展示原因并允许转到手动添加，不要显示虚构地点；行程属于其他用户时 403/404；未登录时应保存公共页位置并引导登录。

**可靠写入**：优先新增明确事务语义的服务端批量添加 API（参见契约）；`clientRequestId` 防重复提交；后端在当前登录用户上下文校验目标行程/天归属、景点真实状态、重复地点与条数限制。若基于现有多次 `createItineraryItem` 做最小 MVP，必须在 UI 明确部分成功与失败、能继续补齐，不能宣称原子操作。**不自动替换用户已有行程**；预览/取消完全只读。

**AI 联动**：在抽屉增加“交给 AI 规划”；仅发送经过明确确认的城市、合法景点 ID 和必要旅行参数。AI 表单预填这些偏好，可编辑后调用现有 `previewAiItinerary`；返回的行程先预览/调整，再经现有 `importItinerary` 保存。原已有 `clientRequestId` 幂等逻辑必须保留。没有 AI Key/服务不可用时，允许手动建行程，给明确可执行说明，不显示假生成结果。不得把攻略全文、私密行程、他人私人数据无提示发送给第三方模型。

**前端建议文件**：`GuideDetailView.vue`、`GuideActions.vue`、`MyFavoritesView.vue`、`AiItineraryView.vue`、`ItineraryDetailView.vue`、新增 `AddToTripDrawer.vue`、`TripSourcePicker.vue`、`useTripIntent.ts`；尽量复用原评论抽屉的模态/焦点模式，而不复制一套半成品。后端新接口及 DTO 由 Codex 主代理负责。

**完成判定**：A 收藏公开攻略后选 2 个景点加入自己的行程；同一请求重复点击无重复记录；B 不可操作 A 的行程；删除/停用/无关联景点均正确处理；关抽屉、刷新、重新登录后数据正确。AI 关闭时手动路径完整可用。

## 3. P0：图片与信息流性能（建议 M16.3）

先**测量**瀑布流首次请求的字节数、实际图片解码尺寸与瓶颈。优先统一固定容器比例/正确 `loading`、`decoding`、`srcset/sizes` 和懒加载策略；需要时由服务端**受控生成**缩略图尺寸（限定几档，去 EXIF，限定 CPU/内存/文件格式），保留现有原图与 M14 灯箱全高清查看。URL 仍为受管路径并经过白名单；不要直接把不可信 URL 送进图像处理库。不得删除原图、丢失作者和来源许可；图片失败不导致瀑布流重排抖动。

先做真实 Lighthouse/Web Vitals 记录（以可复现环境为准），再给出优化前后条件相同的对比；不可把“更多 skeleton”当性能优化。检查 360/390/430/768/1024/1440px、浅深色与自定义主题；尊重 `prefers-reduced-motion`。

## 4. P1：评论回复、@ 提及与消息中心（建议 M16.4）

**不要仅增加按钮。** 当前 `CommentController` 仅有一级纯文本评论创建/列表/本人删除，消息/回复需新增可验证的后端数据模型、版本化迁移、权限与测试。设计一个层级受控的回复机制（最多二级展示、明确 parent/root ID 约束），仅将真实 `@username` 映射到公开有效用户，避免泄露私密信息和恶意提及刷屏；评论编辑、点赞回复、关注等没有列入 P0，不应被假定已存在。

通知仅发给事件相关者；评论/提及通知去重，服务端分页、未读计数、标记已读、已删除目标回退和鉴权隔离；匿名不访问。若增加关注系统，必须单独经过数据模型/用户授权审查，**不要默认用户已经关注任何人**。消息组件支持抽屉或页面，并和 M13 评论抽屉深链联动。先做好权限、频控、举报/治理路径的最小设计，再上线。

P1 可分独立 PR/提交；若无法安全完成，说明 P0 已交付、P1 暂缓，不得声称全部功能完成。

## 5. P1：分享 / SEO / 创作者体验

分享有复制链接与 Web Share（设备支持时），显示用户可复制、落地的真实地址。完善文章可公开的标题、描述、OG 图、canonical，谨防把私人行程和草稿暴露给爬虫。SPA 中**仅客户端设置** OG 元素不足以保证社交平台正确抓取；若没有 SSR/服务端渲染，提供明确服务端 HTML/分享预览实现或记录限制，不要伪称 SEO 全覆盖。

创作者主页可增加公开作品筛选、带来源的旅行足迹和可选公开简介；不展示私密收藏、行程、登录权限字段、后台标记或隐私 IP。保持个人资料页和公开主页权限分离。
